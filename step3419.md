# Fix: invalid default Gemini model name silently kills all LLM extraction

## Bug 1 — `gemini-3.5-flash-lite` is not a real model; every Gemini call fails silently

**Files:** `fact-knowledge-layer/src/fkl/config.py`,
`fact-knowledge-layer/src/fkl/providers/gemini_provider.py`

Both `Settings.llm_model`'s default and `GeminiProvider.__init__`'s
`model_name` default are set to `"gemini-3.5-flash-lite"`, which does not
exist as a callable Gemini model. `.env.example` correctly suggests
`LLM_MODEL=gemini-2.0-flash`, but that's only a template — if the actual
`.env` in use doesn't explicitly set `LLM_MODEL`, the code's own fallback
silently substitutes the broken name. Every `generate_content()` call then
raises, isn't recognized as a 429 so isn't retried, gets caught by the outer
`except Exception` in `extract_facts()` / `extract_from_image()` /
`canonicalise_metric()`, and returns an empty/fallback result — with only a
`logger.error`/`logger.warning` line, no user-visible signal. This has been
silently disabling all LLM-dependent extraction and matching.

**Required fix:**
1. First, confirm the actual currently-valid model identifiers by checking
   Gemini's model list (`genai.list_models()` or the current API docs) rather
   than guessing again — don't just swap one hardcoded string for another
   assumed-correct one.
2. Update both defaults (`config.py`'s `Settings.llm_model` and
   `GeminiProvider.__init__`'s `model_name` parameter) to that confirmed valid
   model name. Keep them in sync — better yet, remove the duplicate default
   from `GeminiProvider.__init__` entirely and require `model_name` to always
   be passed explicitly from `Settings`, so there's only one place this string
   can go stale.
3. **Fail loudly instead of silently on a bad model name.** In
   `GeminiProvider.__init__`, after `genai.GenerativeModel(...)`, make one
   cheap validation call (or call `genai.get_model(f"models/{model_name}")`)
   and raise a clear `ValueError` at startup if the model doesn't exist —
   the same way `config.py` already refuses to start without an API key. A
   bad model name should crash on boot, not silently degrade every extraction
   call for the life of the process.
4. In `_generate_with_retry()`, distinguish "model not found / invalid
   argument" errors from rate-limit errors explicitly (check for `404` or
   `NotFound` / `InvalidArgument` in the exception type or message) and raise
   a distinct, clearly-labeled exception rather than letting it fall through
   the same generic path as a transient failure. This is what would have made
   the bug visible immediately instead of looking like "the LLM just didn't
   find anything."
5. Add one integration test, gated behind an actual API key being present in
   the test environment (skip otherwise — don't make CI require a paid key),
   that instantiates a real `GeminiProvider` with the configured default model
   and makes one trivial `extract_facts()` call against a short synthetic
   block with an obvious fact in it, asserting a non-empty result. This is the
   test that would have caught this — every existing test uses
   `FakeLLMProvider`, so an invalid real model name is invisible to the suite
   by construction.

**Don't:**
- Don't just fix the default and move on — the silent-failure pattern (any
  exception → empty list, logged but not surfaced) is what let this run
  undetected across multiple ingestion sessions. Add the loud-failure-at-boot
  check even though it feels like it's outside today's specific bug.
- Don't add a fallback that quietly switches to `FakeLLMProvider` if the
  configured Gemini model fails — that would reintroduce the same silent
  degradation one layer up.

## Bug 2 — Corrupted/garbled text getting accepted as a table_rule fact (Meridian document)

**Files:** `fact-knowledge-layer/src/fkl/pipeline/parse_pdf.py`,
`fact-knowledge-layer/src/fkl/pipeline/extract_table_facts.py`

Ingesting `04-unseen-meridian-coop-notice.pdf` produced two accepted facts
with `entity_raw` as a run-on sentence fragment, `metric_raw` as a scrambled
phrase, and `period` reading `"OCERY"` — a fragment of "GROCERY" that's been
character-interleaved with adjacent text, the same corruption pattern the
answer key predicts for the annual report's table header. Here it happened on
ordinary paragraph text in a different document, and — unlike prose blocks,
which go through `_metric_in_text()`'s strict content-word grounding check in
`ground_candidates.py` — the `TABLE_CELL` branch of `ground()` only validates
that the value matches the stored cell value, with no equivalent check that
the surrounding row/column header text is coherent.

**Required fix:**
1. Add a coherence check before a block is classified as `TABLE_CELL` in
   `parse_pdf.py`, or as a pre-condition in `extract_table_facts.py`: if a
   detected row/column header contains a high proportion of dictionary-word
   boundary violations (e.g., no space-separated token in the header is
   longer than ~2 characters, or reversed/interleaved patterns are detected
   via a cheap heuristic — check for runs of uppercase letters isolated inside
   lowercase words, since that's the specific corruption signature seen here),
   flag the block as `parse_quality = "suspect_interleaving"` rather than
   treating it as a normal table cell.
2. In `ground_candidates.py`'s `TABLE_CELL` branch, if
   `block.table_context.parse_quality == "suspect_interleaving"` (or
   equivalent flag), reject with a new reason code —
   `"suspected_text_corruption"` — rather than proceeding to value-match
   scoring. This is a stronger, more honest Case #4 story than the one in the
   answer key if it's caught and disclosed instead of silently accepted.
3. Do not attempt to "fix" or de-interleave the text automatically — detect
   and abstain, consistent with the rest of the system's honesty invariant.
4. Add a regression test using this exact document (or a synthetic block with
   the same corruption pattern) asserting it's now rejected with
   `"suspected_text_corruption"` rather than accepted.

**Don't:**
- Don't apply this check to genuinely well-formed table headers with
  legitimate short abbreviations (e.g. "Q1", "FY24") — tune the heuristic
  against real examples from the existing starter datasets and the Solstice
  fixtures to avoid false-positive rejections on normal tables.
